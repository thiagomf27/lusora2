# Decision Log

What's settled, and why. Changing any of these requires a new entry with
the reason.

| # | Decision | Why (short) |
|---|---|---|
| D1 | Greenfield monorepo; old repos are reference material | Contract drift between repos was experienced directly; one commit = contract + both sides |
| D2 | Deterministic orchestrator; LLMs only as 3 bounded agents (script, beat planner, editor chat) | Farm economics: control flow must cost $0/video and be reproducible; OpenMontage's agent-as-orchestrator taxes every video and can't run unattended |
| D3 | DB = control plane (Postgres), files = data plane | Roles/queue/costs need queries; media needs a filesystem; folder-as-truth keeps resume/manual-first |
| D4 | Postgres + pgvector, docker-compose, identical local/VPS | Library already requires it; concurrent writers (API + worker) rule out SQLite |
| D5 | Beat sheet → deterministic compiler → strict edit plan | AI does judgment, code does arithmetic; solves LLM-format pain; Kinema (beats) and OpenMontage (scene_plan→edit_decisions) independently converge on it |
| D6 | Strict schema'd edit plan retained as THE render artifact | Modularity keystone: any planner × any editor × multiple renderers; rejected: code-gen per video, imperative-only editing, native OTIO |
| D7 | ffmpeg is the DEFAULT renderer; Remotion is the premium path; routing by plan capability | Render compute is the main per-video cost; most farm videos are simple; parity trade-off accepted for simple videos |
| D8 | Effects = catalog components with when_to_use rules + semantic props; theme tokens own ALL appearance | Removes the LLM's weakest skill (consistent taste) from its job; brand consistency by construction; hallucinated effects can't pass validation |
| D9 | Pacing/density are NUMBERS in style packs, enforced by compiler/validator | Turns pacing from advice into a guarantee; enables per-video "more/fewer animations" as a config dial |
| D10 | Personalization = 4 data layers (channel, source policy, theme+style pack, component packs); only packs are code, shipped via git | Channels differ by data, not deploys; UI code upload rejected (security + catalog integrity) |
| D11 | Library stays a separate service behind its HTTP API; beats' visual_intent is the search query | Persistent library beats per-project corpora on cost; two consumers (worker+UI) need one API; boundary already proven |
| D12 | Source policy = ordered chain + filters per asset class, min_score fallthrough, chain-exhausted = fail loud | Order expresses all combinations without enums; honest fallback needs a threshold; silent placeholders reach review unnoticed |
| D13 | Cost lifecycle estimated→reserved→actual + pre-spend budget gate | A budget you check after spending is an alarm, not a budget (pattern adopted from OpenMontage) |

| D42 | Prompts become data: ONE file per prompt, typed by role, in `contracts/prompts/<role>/<name>.json` (closes OQ-22a/b) | Principle 4 — prompts were the only personalization layer needing a deploy. Per-role, not per-channel bundles: the script prompt is the one with many variants, and bundling would copy the planner prompt for every new voice. Files, not DB rows: git history + CI schema validation, same as themes/style packs/component packs (D10) |
| D43 | A prompt splits in two: the voice/creative half is editable data; the JSON shape, HARD RULES, component menu and op vocabulary are welded — always appended by code, never shown as editable text (closes OQ-22c) | A UI edit that breaks the output contract would silently burn all three repair attempts and surface as a stage failure; the constrain/validate principle (5) has to hold even when a human writes the prompt |
| D44 | Prompt resolution = per-video override → channel → style pack → built-in default, first hit wins; the resolved **text** (not the name) is snapshotted into `cfg.json` at enqueue (closes OQ-22d) | Same override ladder as the rest of personalization; text-snapshot because prompts will be edited far more often than themes — Principle 7 (an edit never changes an in-flight video, a re-run reproduces the old words) is worth more than the few kilobytes |
| D45 | Script target length lives in the style pack, with a per-video override (closes OQ-23) | Length is part of a pack's shape, next to the pacing numbers it interacts with; mirrors `overlays.density` as a per-video dial. Unblocks long-form channels |
| D46 | Theme gains `surface` (radius, fill, accent_rule) and `motion` (entrance, easing, per_component) — six optional enum tokens, all defaulting to today's hardcoded values (supersedes D30, reopens and re-closes OQ-10) | Presentation style ("clean and serious" vs "punchy and engaging") is a real personalization axis that D30 had no slot for, and the only alternative was duplicating the whole catalog per look — which would pollute the planner's menu with siblings sharing `when_to_use`, cost tokens on every plan call, and render nothing without templates. The renderer receives only `{plan, theme, assets}`, so appearance tokens have exactly one legal home. Enums not numbers (a word keeps meaning one thing); optional with today's values as defaults (old themes render identically, unconverted components ignore them); `entrance` is a request that degrades to `fade` where a component cannot honor it. Zero ffmpeg cost — overlays already force the Remotion route (D31 unaffected) |
| D47 | Motion ROLES (`per_role` keyed by title/data/card/label, mapping to the catalog's clusters) are designed but NOT built; `motion.per_component` ships first. Trigger to build: two or more themes carrying override maps longer than ~6 entries | Roles are the right shape at scale — 4 entries instead of 26, and a new component inherits its cluster's motion with no theme edit — but at today's component count the flat map is smaller in both code and concept. Recording the target shape now keeps the migration cheap; building it now would be solving a problem no theme file has yet |
| D48 | Sound is a FOURTH data layer: a **sound pack** (files + cue/bed vocabulary, git-versioned like a component pack) is the menu; the **theme** gains `sound` (which cue for which entrance, mood→bed, the gain numbers); the **style pack** gains `sfx`/`music` (how often, how long); the **channel** keeps the master on/off and a trim. Cues and beds are placed by the COMPILER as concrete `sfx[]`/`music[]` items, never resolved at render time | Sound is a look, and the existing three-layer table already says where a look lives — inventing a fifth concept would have been the expensive answer to a question the table already answers. Compile-time placement is the load-bearing choice: a cue in the plan is addressable by the editor, survives a per-beat recompile under the D14 lock rules, and mixes identically on both render paths; a cue resolved inside the Remotion composition would be none of those and the ffmpeg path could not see it at all. The alternative — nesting a `sound` field on `overlayItem` — was rejected for the same reasons: invisible on the timeline, unmovable on its own, and duplicated in two renderers |
| D49 | Ducking is a **computed `gain_envelope`** on each music item — piecewise-linear absolute-time points the compiler derives from the real per-sentence TTS timings — not a sidechain compressor. Plus one `loudnorm` pass to -14 LUFS on the finished mix, on both paths | The timings are already exact, so the duck is arithmetic, and Principle 3 says code does arithmetic. A compressor would be nondeterministic, would sound different on the two render paths, would be invisible in the plan and uneditable in the UI. -14 LUFS is YouTube's target, so delivering at it means the platform's own normalization leaves the mix alone — most of the perceptual gap between "auto-generated" and "produced". The theme's `music_duck`/`music_lift` are ABSOLUTE levels and the channel's `default_volume` is a trim: two absolute levels multiplied together is what buries a bed 40 dB under the voice |
| D50 | The LLM never names a sound. Its whole contribution is `mood` per beat (a free string, unknown values degrading to `neutral`); the compiler groups contiguous same-mood beats into spans with a minimum length, and the theme maps mood→bed | Sound selection is consistent taste — exactly what D8 removed from the model's job — and a cue menu in every planner prompt would cost tokens on every call. `mood` was already in the beat sheet, already written by the planner, and read by nothing; this gives it its first consumer. Degrading rather than failing because a planner writing "ominous" instead of "tense" has made a reasonable word choice, and failing a whole video over vocabulary would be absurd. The span floor exists because a two-beat mood blip would otherwise restart the bed and the score would read as a mistake |
| D51 | Per-beat hold bounds are style-pack DATA (`pacing.hold_floor_ratio` / `hold_ceiling_ratio`, both defaulting to 0 = off, shipped packs at 1.0 / 1.5), enforced by the compiler after alignment and re-checked by `validate_plan`; a sub-floor beat MERGES into its neighbour's visual slot without rewriting the beat sheet, and an over-ceiling slot is divided into equal slots | Beat duration is the one pacing number nobody authors: the planner writes a span of script and the SRT decides how long it takes to say, so `min_hold`/`max_hold` were advice about a number that emerged after the fact — beats landed at 0.8s (a flash) and at 14s (one long sentence, no boundary to cut at, dead air). Merging at the VISUAL-slot level rather than in `beats.json` is the load-bearing choice: the beat sheet stays the validated artifact whose verbatim, ordered, gap-free coverage of the script is the whole contract, so the absorbed beat still owns its overlay and its mood and only a CUT moved. Ratios rather than absolute seconds because the numbers must stay consistent with the min/max they qualify; 0 as the schema default because a style pack is snapshotted at enqueue and an in-flight or re-run video must compile byte-identically (Principle 7); `locked` items exempt from the validator because a human who dragged a cut has made a decision that outranks the pack (D39) |
| D52 | Long scripts are planned in CHUNKS (`planner.chunk_target_beats`, default 30), and WHERE the chunks are cut is chosen by a cheap **spine** pass — a fourth prompt role but still the second agent: one call over the whole script returning section boundaries as sentence INDICES plus a one-line summary each, sharing `planner.llm`/`model`, validated by arithmetic, degrading to the deterministic word-balanced split on any failure. Each section is planned and validated on its own, then the merged sheet runs the unchanged `validate_beat_sheet` | One call had to emit the entire verbatim-covering sheet, and at doc length (8–12 min) a single dropped sentence fails full coverage for the WHOLE video, three repair attempts over — the failure is global while the mistake is local. Chunking makes failures local and repairable; cutting at even word counts, though, hands a planner half a movement and it plans towards nothing, which is what the spine fixes. Indices rather than echoed script text is the load-bearing choice: the answer is checkable by arithmetic instead of string matching, the call stays cheap however long the script is, and a malformed spine is detectable rather than plausible. It cannot take control (D2) — code decides the sections, splits any the spine made too big, and falls back silently — and it never touches the contract boundary: the merged sheet is judged by exactly the validator a single call was judged by. Whole-video checks (beat-count range, overlay density) are deferred to that merged pass, because each grants a slack term that would otherwise be handed out once per chunk |
| D53 | Beat sheet **v1.1**: a beat may carry `queries[]` — 2–3 short keyword searches — alongside `visual_intent`. Each source declares which it wants (`query_kind`: the library and image generation take the intent, stock takes keywords), keyword sources try the queries in order before the chain falls through, and a v1.0 beat derives keywords from its intent. v1.0 stays valid | One scout sentence was doing three incompatible jobs: a vector query (which wants the whole description), an image-generation prompt (same), and a keyword search (which wants 2–4 words). Pexels matches WORDS — handed "aerial view of a 1940s industrial district, smokestacks, workers assembling aircraft wings" it returns whatever shares "view" and "of", which is how a man at a desk arrived in a wartime documentary. Splitting the field rather than post-processing the sentence keeps the model doing judgment (which two words name this shot) and code doing arithmetic; deriving keywords deterministically when the field is absent is what keeps manual-first true and lets the change land without reprocessing anything. Trying the alternates inside a source, not across sources, follows D12: the chain is ordered by preference, so a second phrasing of the right shot is worth more than the first phrasing at a worse source |
| D54 | A per-video **used-asset ledger**, rebuilt from the plan (not a new artifact), threaded through `resolve_assets`: a source walks its ranked results and skips any asset id this video already used within `source_policy.visual.dedup.reuse_window_items` (default 0 = the whole video), and optionally any candidate closer than `min_hamming_distance` (default 0 = off) to an earlier shot by 64-bit dHash of one frame | Per-beat resolution is independent by design — D12 is a chain per item — and that independence is exactly what makes two adjacent beats about the same subject fetch the same clip, or the same library segment appear three times in eight minutes, which reads as a mistake rather than as a motif. Rebuilding the ledger from the plan rather than keeping a file beside it follows Principle 1: the plan already records every asset's provenance, so a worker killed mid-stage resumes with what it had, and there is no second place for the truth to live. Walking the ranked results instead of failing is what keeps D12 honest — a used segment is worse than the next one down, but still better than falling through to a worse SOURCE. The perceptual check is off by default because it costs one wasted download per rejection and its threshold is a matter of taste per channel; both numbers are channel data, never constants (Principle 4) |
